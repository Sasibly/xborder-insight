## P3b 接入控制（鉴权 + 限流 + 配额）— 完成

**新增**：迁移 v5（`api_keys` + `rate_limits`）、`security/{keys,quota}.py`、`scripts/keys.py`（create/list/revoke/stale）、`api.Principal` + `current_principal` 依赖。

**四个设计决定**
| 决定 | 理由 |
|---|---|
| 租户只从密钥派生，请求体带 `tenant_id` → 422 | 「允许客户端声明自己是谁」等于没有隔离 |
| 越权一律 404（`get_scoped`） | 403 会确认 job_id 存在，等于给探测接口 |
| 限流落库（`UPSERT ... RETURNING`） | 放内存：重启重置、多实例各算一份 |
| 配额聚合 `jobs` 台账，不建计数器 | 计数器必然漂移，配额错了要么少收钱要么误伤 |

**关键性质**：被拒的请求也计数（先提交再抛 429），否则「一直重试」永远停在第一个请求，限流失效。

**默认值站安全侧**：`AUTH_REQUIRED` 默认 mock 关 / live 开；关闭时启动日志 `auth.disabled` + `/ready` 返回 `auth=disabled` 双留痕。`SYNC_ANALYZE_ENABLED` 同理（live 下默认关）——同步分析不落台账、绕过配额。

**实测（真实服务 AUTH_REQUIRED=true）**：无 key→401+`WWW-Authenticate`；有效 key→202→1 次轮询 succeeded；另一租户读同一 job→404；rpm=5 第 6 次→429 `rate_limited` + `Retry-After: 42`；quota=1 跑完后→429 `quota_exceeded`，同时刻 decision 仍 202；额度耗尽后重放→202 `idempotent_replay=true`。

**顺手修**：① 前缀吊销原先只查未吊销 key，运维脚本重跑报「找不到」→ 改幂等 + 仅在歧义时拒绝；② 同步分析关闭时替代路径只写在 `detail`（对外不可见）→ 并入 `message`；③ `test_quota` 断言在退化时抛 `TypeError` 而非可读消息 → 改为先断言行存在。

**负向验证**：短路归属校验→2 红；被拒不计数→1 红（消息直接写「限流可以被一直重试绕过」）。恢复即绿。

**状态**：251 passed + 1 xfailed，四层门禁全绿，F1 仍 0.8108，迁移到 v5。冒烟密钥已全部吊销。

## 聚类阈值标定（2026-11-18 傍晚）

**先纠正自己的一个错误判断**：我最初说「F1 0.8108 是 hash embedding 跑出来的」——错的。
读 `scripts/run_eval.py` 确认：F1 只来自抽取链路（LLM 输出标签 vs gold），聚类完全不参与。
所以换 embedding / 调阈值 / 改分组逻辑，都不会让 F1 动。用这个数字验收聚类是错的。

**真正的窟窿**：聚类零评测。阈值 0.28 的来源是一句手测注释；`.env.example` 里
「换 dashscope 应提到 0.55~0.65」如果照做会立刻出错——实测无关句对相似度就在 0.43~0.57。

**做法**：先建标注集，再标定。
- `data/eval/cluster_evidence_live.jsonl`：live + qwen-plus 实抽 51 条 evidence 后**冻结**
  （不冻结无法做「只换一个变量」的对照；不用 mock evidence，因为那是关键词规则的原文切片，
  分布与真实模型输出不同）
- `data/eval/cluster_pairs.jsonl`：120 对，同 59 / 异 61
- 判定标准一条：**同一条改进行动能同时解决这两条反映的问题吗**（不用「语义接近」，
  否则「充电快」和「充电慢」字面最接近、经营上相反，会被判同类）

**三个结论**：
1. hash 无排序结构：同主题 P50 0.147 / 不同主题 P50 **0.160**（反了）→ 只能当离线占位
2. 极性必须进分组键：43 对跨极性、判同主题 **0 对**；ARI hash 0.113→0.535、dashscope 0.195→**0.767**
3. 阈值 0.65（不是 ARI 最优的 0.56）：0.56 时 size_fit 四条合成一簇含「太大」+「太小」，
   机会点不可执行；0.65 的代价是 9 个漏合（7 个集中在 build_quality 一条链）。

**方法学教训（最有价值的一条）**：第一版用 pairwise F1 选阈值，选了 0.56 且 F1 0.868，
但那时簇数 16 而 gold 23——**聚类等于没做**（每组恒 1 簇，R 恒为 1.0）。
改用 ARI 才看出来。指标选错会让错的方案看起来最好。

**能力边界**：最优配置仍有 13 对误合并，全是「文本说的是同一件事、业务不同」
（线圈烧毁×水泵失效×滤芯堵塞 8 对、渗漏×溢出 2 对、太大×太小 2 对、整体贵×耗材贵 2 对）。
向量认为它们像是对的，它读不出部件与成因。这是 embedding 的边界，不是调参问题。

**代码**：`analyze.py` 分组键 `label`→`(label,polarity)`；`Theme.polarity`；
`config.CLUSTER_THRESHOLD_BY_PROVIDER`（hash 0.12 / dashscope 0.65）+ `cluster_threshold_source`；
`/ready` 与 `params_snapshot` 回显来源；`.env.example` 删掉写死的 0.28（复制即覆盖的静默陷阱）。

**负向验证**：hash 阈值改 0.65 → ARI 0.058 vs 0.535 报红；分组键退回 label → 极性 `mixed` 报红。

**修掉文档里一个错误承诺**：`test_cluster.py` 那条「换向量会失败提醒重标定」是假的——
它只测 hash，换向量不会红。已在交接摘要改正，并说明分布级守卫在 `test_cluster_eval.py`。

   我原来的判断错了一半：以为这行只是"习惯写法"，实际它是**构建的第一步外网依赖**。

5. 卡在内存：物理 15.9 GB / 可用 **1.2 GB** / `vmmem` 6 GB。构建时 VM 崩

## Docker 再次重启后的环境状态（2026-11-18 21:10）

用户重启 Docker 后五个容器全部自动 Up（mysql/qdrant/kibana/elasticsearch/embedding），
但**环境仍不可用**，两个独立原因：

1. **Docker Hub 依然不通**：`docker manifest inspect python:3.13-slim` → `registry-1.docker.io EOF`。
   重启 Docker 不会改变这一点——这是网络出口问题。默认基础镜像那条待办**继续阻塞**。
2. **embedding warmup 顶爆 VM**：bge-large 在 candle CPU 后端 warmup 报 `Warming up model` 后
   再无输出，随后 daemon 全线 500（`/containers/json`、`/info`、`/images/json`），容器全部消失。
   VM 上限仍 5.79 GB，五个容器占 4.2 GB，剩下约 1.5 GB 不够 bge-large 载入。
   → 结论：**ES + kibana 与本项目无关，应当停掉**，别每次重启都跟着恢复。

**踩到的新坑（重要）**：我执行 `docker desktop restart` 想恢复 daemon——它**先停引擎、再启动**，
启动阶段要调 `wsl.exe`，被安全策略黑名单拦截 → 引擎永久停在关闭状态，只能用户手动从 UI 打开。
**教训：`docker desktop restart` 在本机等于"关机"，不能用来修 daemon。** 要么让用户手动点，
要么直接停无关容器腾内存。这条写进记忆，避免下次重犯。

**代码基线未受影响**：`.venv` 跑全量测试 280 passed + 1 xfailed，8.70s，EXIT=0。

**根因找到了（21:35）**：`~/.wslconfig` 写着 `memory=6GB / processors=2 / swap=2GB`。
所以 VM 上限 5.79 GB 不是 Docker Desktop 设置，是这个文件。五个容器（ES 1.7 + embedding 1.7
+ kibana 0.57 + mysql 0.21 + qdrant 0.03 ≈ 4.2 GB）+ bge-large warmup 峰值 ~2.5 GB
→ 6 GB 装不下 → OOM 打死 containerd → 每次开 Docker 都是「先正常跑 1 分钟，再全体 500」。
**「容器自启」不是错，自启后必然 OOM 才是。** 宿主 15.9 GB / 8 核 16 线程，可用只剩 1.2 GB，
所以不调大 memory，改为把 ES + kibana 的 restart policy 设为 no（需引擎可用时执行一次）。
已把 `processors` 2→6（不占内存、warmup 快数倍），备份 `~/.wslconfig.bak-20261118`。

**环境已修复（21:55）**
- `docker update --restart=no elasticsearch kibana` + `stop` → 只剩 mysql/qdrant/embedding，
  内存 1.6 GiB / 5.79 GiB，余量充足；以后开机不再自启 ES+kibana，OOM 循环断掉。
- **新踩的坑（诊断上值一条）**：重启后三个容器在宿主机「端口能连、HTTP 空回复（curl exit 52）」，
  但 `docker exec` 进去 `/health` 是 200 —— 是 **Docker 启动瞬间由 restart policy 拉起的容器，
  docker-proxy 端口代理绑定失效**，不是容器或网络问题。`docker restart <单个容器>` 即重建代理
  （qdrant 6333 重启后立刻 200，验证有效），不必重启 Docker Desktop。
- **另一个判据**：TEI 的 HTTP 服务要等模型 warmup 完才 bind `:80`，warmup 期间（约 4 分钟）
  宿主机访问必然 000。**不能把 warmup 期间的 000 当故障**——先看日志有没有 `Ready`。
- 最终实测：embedding `/embed` HTTP 200、1024 维、0.43 s。
- Docker Hub 仍不可达（`registry-1.docker.io` EOF，21:55 复测），`python:3.13-slim` 那条继续挂起。
