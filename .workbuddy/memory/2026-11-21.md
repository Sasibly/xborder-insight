## 聚类侧扩标：216 条 / 77 簇 / 354 对，阈值 0.65 → 0.72

**先说结论**：阈值从 0.65 改成 **0.72**（ARI 0.240 → 0.357，bootstrap CI [0.68,0.74]）。
但用户原定的「收紧到小数点后两位」**没达成，原因是方法上限而非标注量**——这个负面结论
比阈值本身值钱，已写进 `docs/05` 第 7 节。

**三处结构变更，每处都是被数据逼出来的**：

1. **标注单位：下标对 → 主题簇**。`SAME_PAIRS` 的 (label,a,b) 成本 O(n²)，且新增一条 evidence
   会在组内新增 k 对，默认判成「不同主题」——若其实是同主题就是凭空造出漏检，F1 只轻微下降不报警。
   改成每条 evidence 归属一个簇后 O(n)，pairs 无损派生。**验证过等价：反推 23 簇再派生回 120 对，逐对零差异。**

2. **标注粒度：粗簇 → 部件级**。三种粒度实测（`build_quality` 31 条）：
   粗簇 ARI 0.460 但 gold 只有正/负两组（**聚类按极性分就满分，零区分力**）；
   部件级 0.173；部件×失效 0.182（多数单例不可学）。选部件级。
   v1 的 `flimsy_build` 把「连接器裂/内部松/盖扣不紧/有毛刺」塞一簇，违反它自己声明的规则。

3. **分组口径：label → (dataset,label,polarity)**。生产 `analyze_reviews` 一次只处理一个 dataset。
   导火索是 label 跨品类**语义漂移**：`charging_speed` 在无线充=充电慢、咖啡机=出水慢、
   电水壶=烧水慢、扫地机=吸力弱。代价：v1 的 23 对跨品类对退出，**v1 0.65 与 v2 0.72 不可直接比**。

**关键数字**：
- evidence 51 → 216（6 品类；新 165 条由 live 抽取产出，旧 51 条原样保留）
- 主题簇 77 个；pairs 120 → 354 对（53 组，平均 4.1 条/组，同 125 / 异 229，正例 35.3%）

## FBA 四维费率维表（迁移 v9，提交 e9a5c72）

**缺口来源**：m0007 把「费率是函数」做成了断言式区间报错，但 FBA 费是四维
（尺寸段 × 重量 × 价格带 × 时段），`UNIQUE (param_key, marketplace)` 连分段都装不下。

**新表 `fba_fee_schedule`**：三维度用 `CHECK ... IN (...)` 收成枚举；
`verified` 三闸与 cost_params 同构；`per_increment_usd > 0` 必须同时给 `increment_oz`
（否则计价函数无法收敛，且留下语义含糊的半行）。

**三条口径决定（面试素材）**：
1. 重量用**闭区间**，相邻档共享端点时取起点更大者。官方写「8 to 12 / 12 to 16」，
   12 本就落在两档表述里。改半开区间就要回答「4.0000001 oz 算不算 4 oz 以内」——
   答案取决于浮点表示，不取决于业务。代价：审计时共享端点不算重叠，
   判定是 `prev.max > cur.min` 而非 `>=`。
2. **缺口绝不外推**到相邻尺寸段/重量档。外推结果是正常数字，只错一个量级。
3. 时段由**发货日期**决定，不由「今天」——否则同一笔报价跨 10/15 重算就变价。
   `quote()` 因此是纯函数，可用固定日期断言。

**数据状态**：12 行全 draft（只搬 docs/04 的 4 档锚点），9 处重量缺口
（4–8oz、16–48oz、320oz 以上），其余尺寸段与旺季整段未录。`resolve()` 当前一律 503。
**没填任何估算值**——填了缺口就消失，错误变成静默的。

**已知边界（已写进 docs/04 第 8 节，不藏）**：SQLite 的 `CHECK` 不能跨行查询，
`UNIQUE` 只保证「同起点只有一行」，挡不住 `[0,4]` 与 `[2,6]` 这种重叠，只能由 `audit()` 检出。

**顺手修的**：本地开发库停在 v8 导致 `test_api.py::test_health_and_ready` 报
`db_not_ready`——这是 `/ready` 的正确行为，跑 `scripts/db.py up` 升到 v9 即恢复。
README 里 local 冒烟输出重跑为 v9；docker 段保留 11-19 的 v8 原样并加时点说明（不伪造输出）。

**状态**：353 passed + 1 xfailed；`make check` EXIT=0（F1 0.6070 未变）；迁移 v9，roundtrip 通过。

## 11:40 FBA 未知时给区间（提交 c4f1d07）

用户说「我现在没有真实的 FBA 值」，触发点是上一段把 H2（包装尺寸）列为最影响出结论的项。
顺着这句话去查，发现了比缺数据更糟的东西：

**`CostProfileInput.fba_fee` 默认 0.0**。不填 = 免配送费。实测 FBA $6.5 → 毛利率 23.3%，
按 0 计 → 34.2%，差 10.9 个点，而响应字段完整、精确到两位小数，看不出来。
缺数据会报错，这个不会——这是「缺失 ≠ 通过」真正的破口。

解法是**把「不知道」表达成区间**，不是猜一个值：
- `FeeEnvelope` / `fee_envelope()`：用官方表算包络。每行取重量区间两端各算一次，
  取全样本 min/max。不插值（插值会造出官方没有的费率）、不掺 draft、不跨维。
- 部分已知要能用上：`size_tiers` / `weight_range_oz`。只知道「标准小件」，
  跨度从 $9.46 → $0.72。
- 三值判断：乐观端不达标 → FAIL；保守端达标 → PASS；跨阈值 → UNKNOWN。
  **只有跨阈值的 SKU 才需要量箱子**，H2 因此降级为「先给重量上界」。
- 点值取 high（最贵档）。低估成本不可逆，高估只是错过，代价不对称。

一条要记住的判断：包络宽不是缺陷。宽是因为真的不知道；把它换成窄的假数才是缺陷。
区间两端都是真实格子，所以「按最贵档仍 ≥ 15%」是可证明的 GO，不是乐观估计。
