# 平台系统实施流程与验收标准

> 适用范围：跨境电商选品决策平台（当前已有「评论抽取 → 聚类 → 机会分」管道）
> 目标：从「能跑通的管道」演进为「能持续运行、可复现、可交付的平台系统」

---

## 0. 通用假设

若以下任一假设与实际不符，相应阶段的工作量与顺序需调整。

| 假设项 | 取值 | 说明 |
| --- | --- | --- |
| 平台类型 | B2B 选品决策工具，单租户起步、预留多租户 | 不做面向 C 端的交易闭环 |
| 使用方 | 跨境卖家 / 选品运营 | 只服务「决策」，不承接下单、支付、履约 |
| 业务规模 | 日均任务 < 1000，单次分析 20–500 条评论 | 不进入需要分库分表、消息中间件的量级 |
| 团队 | 1 人全栈 | 所有任务必须可串行、可中断、可单人验收 |
| 技术栈 | FastAPI + SQLite（可切 PostgreSQL）+ 百炼 qwen + 自实现聚类 | 沿用现有代码，不重写技术选型 |
| 部署形态 | 单机 Docker Compose | 不做 K8s、不做多区域 |
| 时间预算 | 4 周（可压缩至 2.5 周） | 按「每阶段可独立交付」设计，随时可停 |
| 数据来源 | 合成样本 + 公开信息 + 人工录入参数 | 不抓取平台前台数据（合规红线） |

**规模假设的意义**：它直接决定哪些模块「必须做」、哪些「做了是过度设计」。日均 1000 任务不需要消息队列，但**必须**有任务状态持久化——这是本清单所有取舍的依据。

## 2. 阶段总览

| 阶段 | 名称 | 目标 | 工期 | 可独立演示 |
| --- | --- | --- | --- | --- |
| P0 | 基线固化 | 把现状变成可回归的基线 | 0.5 天 | 是 |

## 3. 逐阶段详情

### P0 · 基线固化（0.5 天）

**目标**：先把「现在能跑出什么」钉死，否则后面任何改动都无法判断是变好还是变坏。

**关键任务**
1. 记录当前指标快照：F1 / P / R、解析成功率、端到端耗时、调用次数
2. 为已有核心逻辑补最小回归测试：契约解析、机会分公式、清洗去重
3. 固化两条命令：`scripts/demo.py`、`scripts/run_eval.py`

**交付物**
- `docs/baseline.md`：指标快照与运行环境
- `tests/test_contract.py`、`tests/test_scoring.py`
- `pytest.ini` 或 `pyproject.toml` 测试配置

**验收标准**
- [ ] `pytest` 全绿，且测试覆盖契约解析的 4 条分支（正常 / 代码块包裹 / 越界标签 / 非 JSON）
- [ ] `scripts/run_eval.py` 输出的 F1 与 `baseline.md` 一致（误差 0）
- [ ] 新增依赖已写入 `requirements.txt`

**判断依据**：没有回归测试的架构改造，等于在流沙上盖楼。这一步只有半天，但省掉后面每次改动的自我怀疑。

### P1 · 数据地基（3 天）

**目标**：把跨境业务对象变成可持久化的数据模型。**这是全流程的硬阻塞点**，表结构错了后面全部返工。

**关键任务（严格按序）**
1. 定义领域对象：`Product`（ASIN、类目、售价、尺寸重量）、`CostProfile`（采购价、头程、佣金率、FBA 费、退货率）、`CompetitionSnapshot`（评论数、评分、卖家数）、`ComplianceRule`（品类 × 目的国 → 必需认证）
2. 设计表结构与索引（重点：任务表、用量台账的唯一约束）
3. 实现迁移机制（版本化 up/down，禁止手改表）
4. 实现仓储层（查询封装，杜绝 N+1）
5. 落种子数据：2 个品类、4 个 ASIN 的完整成本与竞争数据

**交付物**
- `src/xborder_insight/storage/schema.sql`
- `migrate.py`（`up` / `down` / `status` 三个子命令）
- `repositories.py`（按聚合根分组的查询方法）
- `data/seed/*.json`

**验收标准**
- [ ] `migrate.py up` 在空库执行成功，`down` 能完整回滚，`up → down → up` 幂等
- [ ] 所有外键与唯一约束生效（插入重复幂等键报错而非静默覆盖）
- [ ] 仓储层单测覆盖增删改查与关联查询，且用真实 SQLite 而非 mock
- [ ] 种子数据可通过一条命令导入

**风险**：业务字段想不全，导致后续频繁加列。
**缓解**：成本项按「可配置字典表」设计，不硬编码字段；新增成本项只加数据不加表结构。

### P2 · 业务能力（5 天）

**目标**：让系统能回答「这个品能不能做、能赚多少」，而不只是「有哪些痛点」。

**关键任务（按依赖排序）**
1. **利润模型**（依赖 P1 的 CostProfile）：到手毛利、毛利率、**盈亏平衡 ACOS**

   ```
   落地成本 = 报价 + 头程 + 关税
   退货影响 = 退款冲减 + 处理费 + 退款管理费 + 商品损失 + 头程损失
   毛利     = 售价 − 落地成本 − 佣金 − FBA − 退货影响
   盈亏平衡 ACOS = 毛利 ÷ 售价
   ```

   **贸易术语条件分支**（口径与业务方确认于 2026-11-17，改动须同步本节）

   报价所对应的 Incoterm 决定「哪些成本已在报价里」，不能对任何报价都套同一公式：

   | 术语 | 报价已含头程 | 报价已含关税 | 头程处理 | 关税处理 |
   | --- | --- | --- | --- | --- |
   | EXW / FOB | 否 | 否 | 计入 | 计入 |
   | CFR / CIF / DAP | 是 | 否 | **置零**（避免重复计运费） | 计入 |
   | DDP | 是 | 是 | **置零** | **置零**（避免重复计税） |

   - 建站初期以 **FOB** 为默认口径；默认值必须在响应中回显（`incoterm_assumed`），不得静默填充
   - 含税术语下若仍传入非零税率，模型须发出 warning 而非默默忽略——静默置零会让「以为算了」与「确实没算」无法区分
   - 关税计税基础取申报价值（即报价），不将运费与保险并入完税价格

   **退货影响五段归集**（禁止用单一比率）

   | 段 | 公式 | 基数 |
   | --- | --- | --- |
   | 退款冲减 | 退货率 × 售价 | 售价（性质是交易被撤销，不是费用） |
   | 处理费 | 退货率 × 每件处理费 | 退货件 |
   | 退款管理费 | 退货率 × 费率 × 原佣金 | **原佣金**（按售价取比例会放大一个数量级） |
   | 商品损失 | 退货率 × 不可再售比例 × 报价 | 报价 |
   | 头程损失 | 退货率 × 沉没比例 × 实际头程 | 实际计入的头程 |

   - 只扣四段费用、不冲减退款时，退货率 50% 仍会算出正毛利（实测 +9.54），补上退款冲减后同一情景为 −5.45。这一项缺失会让高退货率品类被判为「可做」
   - 佣金按全额计、未按退货比例退回，因此模型对退货的估计**偏保守**，须在 `assumptions` 中声明

   **负毛利时 ACOS 不返回数值**，返回 `null` 并给出理由：亏损状态下任何广告投入都只放大亏损，「ACOS = −0.20」会被读成「还有 20% 空间」
2. **合规规则表**（与 1 并行）：品类 × 目的国 → 认证清单，用规则表而非模型
3. **决策评分**（依赖 1、2 与已有机会分）：机会分 × 利润率 × 竞争度 × 合规风险 → GO/NO-GO + 理由
4. 把决策结果接入现有看板与 API

**交付物**
- `domain/profit.py`、`domain/compliance.py`、`domain/decision.py`
- `domain/rules/compliance_matrix.json`
- `GET /v1/products/{asin}/decision` 接口
- 看板新增「决策结论」区块

> **P2 现状补注（2026-11-23）**：上面是计划原文，与实现有三处实质差异，不改原文以免丢失当时的判断：
>
> 1. **接口是 `POST /v1/decision`，不是 `GET /v1/products/{asin}/decision`**。原因是没有 ASIN 级数据源——
>    售价、采购价、尺寸重量都是外部事实，`GET` 一个 ASIN 只能返回「我不知道」。改成 POST 传
>    `CostProfile`，缺字段就 422 或 NEED_MORE_INFO，契约上不允许系统自己编。
> 2. **竞争度没有单列成指标**。机会分里已经含提及数与负向占比，再乘一个竞争度会重复计权，
>    且竞争度没有可核实来源。决策只合成三样：机会分阈值、毛利、合规。
> 3. **合规规则落库（`compliance_rules` 表），不是 `domain/rules/compliance_matrix.json`**。
>    放 JSON 里，规则带不了「状态 / 来源 / 生效日期」，也进不了迁移往返校验；落表后
>    `unknown` 与 `clear` 的区别、以及「未核实不得降级」才能被 CHECK 与测试钉住。
>
> 落地记录见 [`docs/03`](03-单人执行版路线.md) §7「P2 落地记录」，逐项对照这份计划。

**验收标准**
- [ ] 利润模型单测覆盖：正毛利 / 负毛利 / 零销量 / 退货率极端值，且边界不抛异常
- [ ] 盈亏平衡 ACOS 与手工计算一致（用种子数据里一个真实 ASIN 验算）
- [ ] **贸易术语分支**：DDP 不叠加关税、CIF/CFR/DAP 不叠加头程；误传税率或运费时发出 warning 而非静默置零
- [ ] **退货五段基数正确**：退款管理费按原佣金取比例（非售价），头程损失按实际计入的头程取比例
- [ ] 负毛利时 `breakeven_acos` 返回 `null` 并附理由，不得返回负数
- [ ] 未知贸易术语返回 422（`input_invalid`），不得漏成 500
- [ ] 每个条件分支都在 `assumptions` 中留下口径记录，结论可事后复核
- [ ] 合规规则表覆盖 2 品类 × 3 目的国，缺失组合返回「未知」而非静默通过
- [ ] 决策接口对同一 ASIN 返回稳定结论（同输入同输出）
- [ ] 每个结论必须带**可解释的理由**，不能只返回一个分数

**风险**：成本参数无真实来源，模型变成「看起来专业但不可信」。
**缓解**：所有参数可配置且标注来源与取值日期；README 明确写「参数为公开信息估算，非实测」。

**判断依据**：这一步是「懂业务」与「会写代码」的分界。利润模型能算对，业务可信度立刻成立。

### P3 · 平台化（6 天）

**目标**：把「同步请求 + 内存计算」改造成「任务化 + 可复现」。**这是能否上生产的分水岭。**

**关键任务（严格按序，后项依赖前项）**
1. **任务模型**：`jobs` 表 + `POST /v1/jobs`（202 + job_id）+ `GET /v1/jobs/{id}` + 状态机 `queued → running → succeeded/failed`
2. **执行器**：进程内异步 worker，从表取任务，支持并发上限与失败标记
3. **幂等**：`Idempotency-Key` 头 + `UNIQUE(tenant_id, idempotency_key)`，重复提交返回同一 job
4. **结果持久化 + 重放**：结果落表；`POST /v1/jobs/{id}/retry`
5. **鉴权**：API Key → tenant，哈希存储，支持吊销
6. **配额与限流**：每日 token 配额、超限拒绝（429）、令牌桶限流
7. **用量台账 + 版本三元组**：每次运行记录 `prompt_version / model / taxonomy_version` 与 token 消耗，支持按租户归因

**交付物**
- `jobs/runner.py`、`jobs/models.py`
- `security/auth.py`、`security/quota.py`
- 迁移 `002_jobs.sql`、`003_auth_usage.sql`
- `POST /v1/jobs`、`GET /v1/jobs`、`GET /v1/jobs/{id}`、`POST /v1/jobs/{id}/retry`

**验收标准**
- [ ] 提交 500 条评论的分析，请求在 200ms 内返回 202，任务在后台完成
- [ ] 同一 `Idempotency-Key` 重复提交 5 次，只产生 1 个任务、1 次扣费
- [ ] 任务失败后 `retry` 能重新执行，且不产生重复计费
- [ ] 无 Key 请求返回 401；超配额返回 429；两者响应体结构一致且含 request_id
- [ ] 用同一 `prompt_version + model + taxonomy_version` 重跑历史任务，结果完全一致
- [ ] 服务重启后，`running` 状态任务能被重新拾取，不永久卡死

**风险**
- 单人项目容易把「任务化」做成半成品（状态存在内存里，重启即丢）→ 缓解：状态一律落表，验收第 6 条专治此病
- 幂等键设计不当（只按参数哈希）→ 缓解：按 `tenant + key` 设计，业务参数变化才换 key

**判断依据**：真实 LLM 下单条评测 1–3 秒，500 条必然超时。同步模型在这一刻就死了，与规模无关，是**物理限制**而非优化项。

### P4 · 交付加固（3 天）

**目标**：让别人能一条命令跑起来，并让系统状态可观测。

**关键任务**
1. 集成测试：启动服务 → 提交任务 → 轮询 → 断言结果与指标
2. `Dockerfile` + `docker-compose.yml`（应用 + 数据卷 + 环境变量校验）
3. `/metrics`：任务数、成功率、P50/P95 延迟、token 消耗、配额余量（Prometheus 文本格式，不引第三方依赖）
4. 文档：README 更新（架构图、启动、验收命令）、`docs/runbook.md`（常见故障处置）

**交付物**
- `tests/test_integration.py`
- `Dockerfile`、`docker-compose.yml`、`.dockerignore`
- `GET /metrics`
- `docs/runbook.md`

**验收标准**
- [ ] `docker compose up` 在干净机器上 3 分钟内可用
- [ ] 容器内 `curl /health`、`/ready`、`/metrics` 均正常
- [ ] `pytest` 全绿，其中集成测试使用真实数据库与真实 HTTP 调用（不 mock 服务层）
- [ ] 杀掉容器后重启，历史任务与用量数据不丢
- [ ] 无密钥、无 `.env` 被打包进镜像

**风险**：容器内 SQLite 路径未挂卷，重启丢数据。

## 4. 模块判定矩阵

### 判据（三条，按优先级）

1. **是否阻塞「跑通」**：不做就无法完成一次端到端分析 → 必须
2. **是否影响结论可信**：不做则数字或结论不可信、不可复现 → 必须
3. **是否只在更大规模才需要**：日均 1000 任务以下用不到 → 暂缓

### 必须实现（核心能力）

| 模块 | 判据 | 依据 |
| --- | --- | --- |
| 结构化抽取 + 契约校验 + 三级降级 | 1+2 | 产品价值本体；已有，只需保护 |
| 人工标注评测集与指标 | 2 | 没有金标准，一切效果声明都是空话 |
| 持久化与任务状态 | 1 | 内存态无法支撑异步与重放 |
| 任务化执行 | 1 | 真实 LLM 延迟下同步模型物理不可行 |
| 幂等键 | 2 | 重复提交重复扣费，直接损失成本 |
| 鉴权 + 配额 | 1+2 | 无鉴权则成本不可控、数据不可隔离 |
| 版本三元组（prompt/model/taxonomy） | 2 | 不做则历史结论永远无法复现 |
| 利润模型 | 2 | 业务结论的可信基础 |
| 合规规则表 | 2 | 跨境特有风险，缺失结论不可用于决策 |
| 迁移机制 | 1 | 无迁移则表结构变更不可控 |

### 暂缓（P1，有收益但非阻塞）

| 模块 | 暂缓理由 | 何时再启动 |
| --- | --- | --- |
| 竞争度指标自动化采集 | 数据获取成本高，可先用人工录入跑通决策链 | 决策链验证通过后 |
| 决策评分加权调参 | 依赖利润/合规/竞争三者齐备 | P2 末 |
| 结果缓存 | 先保证「算得对」，再优化「算得快」 | 成本指标出现压力时 |
| 多品类扩展 | 单品类跑通比多品类半成品有价值 | 核心闭环稳定后 |
| 分语种指标拆解 | 不影响主流程 | 有真实多语言数据后 |

### 无需实现（明确排除）

| 模块 | 排除理由 |
| --- | --- |
| 平台数据抓取（爬虫） | 违反平台条款，且一旦被问「数据哪来的」即失信 |
| 支付 / 计费 / 发票 | 与选品决策无关，属另一个产品域 |
| 多租户前端与权限矩阵 | 单租户起步，后端预留即可，前端做出来只会被追问细节 |
| 微服务拆分 / K8s | 日均千级任务用单机，拆分纯属增加故障面 |
| 模型微调 | 瓶颈在输出契约与评测，不在模型能力 |
| 消息队列（Redis/Celery） | 单机异步 + 数据库状态足够；引入后需额外运维与死信处理 |
| 实时流处理 | 选品是分钟级决策，不是实时场景 |

**关于「不做」的价值**：这七条写在文档里，比多做七个模块更能证明工程判断力。面试追问「为什么不用 Celery」时，有答案远胜于有部署。

## 5. 依赖关系

```
P0 基线固化
   └─→ P1 数据地基（领域模型、表结构、迁移、仓储）
          ├─→ P2a 利润模型 ─┐
          ├─→ P2b 合规规则 ─┼─→ P2c 决策评分 ─→ 接入看板/API
          └─→ P3a 任务模型（jobs 表，依赖 P1 迁移机制）
                    ├─→ P3b 执行器
                    ├─→ P3c 幂等（依赖 jobs 唯一约束）
                    ├─→ P3d 鉴权（可与 3b 并行）
                    └─→ P3e 配额台账（依赖执行器统计）
                              └─→ P4 测试/容器/指标
```

**硬依赖（不可调整顺序）**
- 迁移机制 → 所有建表（含任务表、鉴权表）
- 成本项字段 → 利润模型
- 合规规则表 + 利润模型 + 机会分 → 决策评分
- 任务表 → 幂等（唯一约束依赖表结构）
- 执行器统计 → 用量台账 → 配额判断

**可并行**
- P2a 利润 ∥ P2b 合规
- P3b 执行器 ∥ P3d 鉴权
- 后端接口 ∥ 看板迭代

**可整体跳过而不影响主线**
- P2 竞争度自动化 → 用人工录入替代，决策链仍成立

## 6. 风险登记

| # | 风险 | 概率 | 影响 | 缓解措施 | 触发信号 |
| --- | --- | --- | --- | --- | --- |
| R1 | 业务参数（佣金率、FBA 费）无权威来源 | 高 | 利润结论不可信 | 参数可配置 + 标注来源与日期 + 明确声明为估算 | 算出的毛利率偏离常识（如 >60%） |
| R2 | 表结构反复变更 | 中 | 返工、数据丢失 | 成本项走字典表；变更必走迁移，禁止改表 | P2 期间出现第 3 次加列 |
| R3 | 任务化做成半成品（状态在内存） | 高 | 重启丢任务 | 状态一律落表；验收含重启恢复测试 | 重启后存在永久 running 的任务 |
| R4 | 真实 LLM 延迟/成本超预期 | 中 | 单次分析超预算 | 小模型分流 + 并发上限 + 结果缓存（暂缓项提前） | 单次 500 条成本 > 1 元 |
| R5 | 范围蔓延（不断加功能） | 高 | 永远无法交付 | 本文件的「无需实现」清单即边界，新增须先删一项 | 出现清单外的新模块 |
| R6 | 评测集过小导致指标不稳 | 中 | 简历数字被质疑 | 扩到 200 条；报告置信区间 | 同一改动后 F1 波动 > 0.05 |
| R7 | 单人进度失控 | 中 | 项目烂尾 | 每阶段末必须可演示，任意阶段停止都交付完整闭环 | 某阶段超过预估 1.5 倍 |
