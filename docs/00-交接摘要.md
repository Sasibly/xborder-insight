### 2.2 关键结论（已验证，可直接引用）

1. **实测指标（两套口径，不可混用）**：
   - 200 条 / 6 品类（当前门禁基线，mock）：TP 95 / FP 34 / FN 89，**P 0.7364 · R 0.5163 · F1 0.6070**
   - 42 条旧品类子集（原口径，mock）：TP 30 / FP 2 / FN 12，**P 0.9375 · R 0.7143 · F1 0.8108**（扩集后逐位复现）
   - 200 条 / qwen-plus（live）：TP 150 / FP 42 / FN 34，**P 0.7812 · R 0.8152 · F1 0.7979**
1b. **成本与延迟口径**：mock **70 token/条 · 1.00 次调用/条 · P50 15ms · P95 15ms**；
   live **345 token/条 · 1.00+0.005 次调用/条 · P50 1706ms · P95 2835ms**（SLA 3000ms，余量仅 165ms）。
   成本只报 token 与调用次数，**不折算人民币**——单价需官方口径，未核实不写钱数。
2. **修掉一个真 bug**：极性判定原本只看句内情绪词，`"Takes forever"`、`"does not seal"` 被抽出后判成 `neutral`，评测时被过滤 → 改用**星级兜底**后 F1 从 0.625 升到 0.8108。剩余 12 条漏检全是语义难点（间接表达、中文口语、隐性故障），这是「规则基线与 LLM 差距」的叙事素材。
3. **语义聚类的阈值必须按向量标定，极性必须进分组键**（2026-11-18 首标，2026-11-21 扩集重标）：
   早期阈值 0.28 来自手测几个句子，没有标注集，无法回答「比 0.30 好在哪」。
   216 条 evidence / 354 对（生产口径 `(dataset,label,polarity)` 组内）实测：
   hash 向量的同主题对 P50 **0.140**、不同主题对 P50 **0.187**（反了，没有排序结构，任何阈值都是随机切分）；
   text-embedding-v3@512 为 0.729 / 0.648，阈值 **0.72**（ARI 0.357，bootstrap CI [0.68,0.74]）。
   极性进分组键不是「最好加」而是「必须加」——**「充电快」与「充电慢」相似度 0.872**，
   是本数据全部跨极性对里最高的一对，向量读不出行动方向。
   ⚠️ 单阈值向量聚类**做不到细粒度归并**（能力边界就在大类分桶），详见 `docs/05` 第 7 节。
   主结构仍用 taxonomy 标签聚合，语义聚类只做标签内的场景发现。
4. **机会分用固定公式而非模型打分**：`0.55×提及广度 + 0.35×负向占比 + 0.10×证据强度`。理由：模型打 0–100 分无法解释来源，面试必被问倒。
5. **口径声明**：抽取指标分两套——200 条跨品类（门禁基线，mock，F1 0.6070）与 42 条同品类（原口径，F1 0.8108）；
   live 的 0.7979 是参照数字，**不进门禁**（门禁必须无 Key、无网络可跑）。
   聚类指标来自 **live + qwen-plus 实抽后冻结/扩充**的 evidence 集（`data/eval/cluster_evidence.jsonl`，216 条）。三套口径不同，不可混着引用。
5b. **规则基线的失效点是品类迁移，不是数据量**（11-21 扩集实测）：同品类 F1 0.81 / 新品类 0.54；
   召回 0.71→0.46、精度 0.94→0.67（两头都掉，不是「只漏不误」）。qwen-plus 在同一 158 条新品类上是 0.7766。
   这条比「12 条漏检是语义难点」更硬：不是个别难例，是词表本身不可迁移。详见 `docs/06`。
6. **建模缺陷（P2，已验证修复）**：退货影响最初只扣四段费用、不冲减退款收入，导致 100% 退货率仍算出正毛利 6.89、50% 退货率算出盈利 9.54；补「退款冲减」后为 −23.10 / −5.45，偏差恰为 `退货率 × 售价`。**可用于回答「你怎么验证模型是对的」**：纯函数测试 + 双向断言（修复后亏损 / 摘掉修复项重现旧错值），domain 层不读库所以不依赖参数是否核实。
7. **合规缺失不等于通过**：规则表未覆盖的「品类 × 市场」返回 `unknown` 而非 `clear`；有规则但未核实时同样 `unknown`。「没查到阻断项」与「确认没有阻断项」是两件事——把前者说成后者，是合规系统唯一不可接受的静默降级。
8. **任务化的三个数字**（P3 实测）：同一幂等键重发 3 次 → 队列仍是 1 条任务、`idempotency-replayed: true`；同键换请求体 → 409；模拟 worker 被 kill（running + 租约过期）→ `recover` 重新入队后由另一个 worker 接手完成，`attempts=2`。三件事都不靠「记得清」而靠数据库约束。
9. **决策接口的成本数据由调用方提供**：内置参数全 draft，若强制从参数表读会永远 503 无法验证。改为请求体带 `cost`、响应回显 `data_provenance`，责任边界清晰。实测毛利 31.2% + 机会分 0.66 达标，仍返回 `NO_GO`（合规 2 条 blocker 未核实），headline 注明「核实后可能解除」。
10. **FBA 费不是参数，是四维查表**（11-21，迁移 v9）：塞进 `cost_params` 的任何一个单值，
    都等于替调用方默认了「哪个尺寸、多重、卖多少钱、哪天发货」——换个 SKU 四维全变，
    而返回值看起来一样正常。建 `fba_fee_schedule` 后有三条口径必须写死：
    ①重量用**闭区间**，相邻档共享端点时取起点更大者（官方写「8 to 12 / 12 to 16」，
       12 本就落在两档表述里；用半开区间就要回答「4.0000001 oz 算不算 4 oz 以内」，
       而这个答案取决于浮点表示，不取决于业务）；
    ②**缺口绝不外推**到相邻尺寸段或相邻重量档——外推的结果是个看起来正常的数字，
       只是错了一个量级；
    ③时段由**发货日期**决定而不是「今天」，否则同一笔报价跨过 10/15 重算就变价。
    当前 12 行全 draft、9 处缺口，`make db-fba` 直接列出缺哪几段。
    已知边界：SQLite 的 `CHECK` 不能跨行查询，**区间重叠拦不住**，只能由 `audit()` 检出。

**贸易术语分支**（`incoterm.py`，这张表就是商务知识的可执行版本）：

| 术语 | 含头程 | 含关税 | 处理 |
|---|---|---|---|
| EXW / FOB | 否 | 否 | 两项都计入 |
| CFR / CIF / DAP | 是 | 否 | 头程置零、关税计入 |
| DDP | 是 | 是 | 两项都置零 |

置零不是"忽略"：必须写进 `assumptions`，且误传非零值时要发 warning。理由——静默置零会让「以为算了」和「确实没算」无法区分。

**退货五段**（`ReturnsLoss`）：退款冲减 + 处理费 + 退款管理费 + 商品损失 + 头程损失，各段基数不同（详见 `docs/02` P2 节）。

**开发中测出的真缺陷（重要，面试可讲）**：最初只扣四段费用、收入按 100% 计，导致退货率 100% 仍算出正毛利 6.89、50% 退货率算出盈利 9.54。根因是**退款从未被扣**，偏差恰为 `退货率 × 售价`。补上「退款冲减」后分别为 −23.10 / −5.45。`tests/test_profit.py::test_revenue_reversal_is_what_makes_high_return_rate_lose_money` 双向锁定：既断言修复后亏损，也断言摘掉修复项会重现 +9.54。

**负毛利不返回 ACOS**，返回 `None` + 理由。`ACOS = −0.20` 会被读成"还有 20% 空间"——数值合法、含义相反，这是模型能犯的最危险错误。

**已知保守偏差（已声明，不修）**：佣金按全额计、未按退货比例退回，因此对退货的估计偏保守，真实毛利略高于模型值。这条写进了 `assumptions`。

**合规三态（核心设计）**：

| 状态 | 含义 |
|---|---|
| `blocked` | 命中 blocker（已核实或未核实都阻断，但用 `has_unverified_blocker` 区分叙事） |
| `unknown` | 规则表未覆盖该「品类 × 市场」，**或有规则未核实** |
| `clear` | 无 blocker 且全部已核实 |

`unknown` 必须独立存在：缺失组合静默通过 = 把「我们不知道」说成「没问题」。当前 4 条规则中 1 条已核实（FCC Part 18 + SDoC）、3 条 draft（含 1 条 blocker）→ 该品类仍 `blocked`；`clear` 要求全部规则已核实。

**决策三档 + 否决顺序**：`GO / NO-GO / NEED_MORE_INFO`，顺序**合规 > 毛利 > 广告空间 > 需求**。所有因素都记进 `reasons`，不只记触发否决的那条（只报否决项会让人以为修好它就能做）。阈值 `MIN_GROSS_MARGIN=0.15 / MIN_OPPORTUNITY=0.55 / MIN_BREAKEVEN_ACOS=0.20` 是**业务假设**，随响应返回并标注。

**关键架构决策：成本数据由调用方提供，不从参数表读。**
内置 11 项参数全 draft，若只能从参数表读，接口永远 503 无法验证。改为请求体带 `cost`，响应回显 `data_provenance`——责任边界清晰，不把他人的估算冒充为系统的核实结论。

### P3 已完成内容（2026-11-17，任务化核心）

**迁移 v4**：`jobs` 表 + `runs.job_id/attempt`。表里写死了三条约束：
1. `UNIQUE(tenant_id, idempotency_key) WHERE idempotency_key IS NOT NULL` —— 幂等靠唯一索引，不靠「先查再插」
2. `CHECK (status <> 'running' OR lease_expires_at IS NOT NULL)` —— running 必须有租约
3. `CHECK (attempts <= max_attempts)` —— 重试上限由库保证，代码数错也不会无限重试

**接口**：`POST /v1/jobs`（202）、`GET /v1/jobs`、`GET /v1/jobs/{id}`（含每次执行的台账）、`POST /v1/jobs/{id}/retry`。

**四个关键设计**
| 设计 | 实现 | 面试讲法 |
|---|---|---|
| 幂等 | 直接 INSERT，撞 `UNIQUE(tenant, key)` 后回查 | 「先查再插」在并发下必然漏，让数据库做仲裁 |
| 键复用检测 | 比对规范化 JSON 的 sha256，不同 → 409 | 返回旧任务会让调用方以为新参数生效，实际跑的是老参数 |
| 防卡死 | 租约 + 心跳续租（租约 1/3 周期） | 不续租时任务会在自己还在跑时被别人重新领取，同一份工作付两遍钱 |
| 计费不重复 | `UNIQUE(job_id, attempt)` 部分索引 + `jobs`/`runs` 分表 | 重试是新的 attempt（真的又调了一次模型），同一次尝试只能记一笔 |

**版本三元组**：`prompt_version / model / taxonomy_version` 落 `jobs` 行，且是**内容哈希**（`prompt-xxxx` / `tax-xxxx`），不是手写 `v1.2`。手写号一定会忘记升，忘了升的版本号比没有更糟。

**实测**（mock，离线客户端）：
- 提交 3 条评论分析 → 202 即刻返回 → 轮询 1 次后 `succeeded`，`llm_calls=3`、`total_tokens=153`、`executions=[attempt 1]`
- 同键重发 3 次 → 同一 `job_id`、`idempotency-replayed: true`，队列仍 1 条
- 同键换请求体 → 409 `idempotency_conflict`（带 request_id）
- 模拟 worker 被 kill（running + 租约过期）→ `scripts/jobs.py recover` 重新入队 → 被另一个 worker 接手完成，`attempts=2`

**负向验证**：短路指纹比对后，库层与 HTTP 层各红一条测试；恢复即绿。

**测试**：201 passed + 1 xfailed（新增 `test_jobs.py` 31 条 + `test_jobs_api.py` 15 条）。四层门禁全绿，**F1 仍 0.8108**。

**四个关键设计**

| 设计 | 实现 | 面试讲法 |
|---|---|---|
| 租户不可声明 | 请求体带 `tenant_id` → 422（`extra="forbid"`），tenant 只能从密钥派生 | 允许客户端声明自己是谁，等于没有隔离 |

| 限流落库 | `rate_limits(tenant_id, window_start)` + `UPSERT ... RETURNING` | 放内存：重启重置、多实例各算一份，实际是标称值的 N 倍 |
| 被拒也计数 | 先提交计数，再抛 429 | 回滚掉的计数让「一直重试」永远是第一个请求 |
| 配额查台账 | 直接聚合 `jobs`，不另建计数器 | 计数器必然漂移；配额错了要么少收钱要么误伤客户 |

**为什么入口脚本负责迁移，而不是应用启动时自动迁移**：应用内自动迁移等于「任何一个跑起来的进程都可能改库结构」，多实例时就是两个进程同时往一个库上跑 DDL。放进入口，迁移时机只有「容器启动」一个。迁移失败 → 脚本退出 → 容器退出 → 编排层重启，比「起得来但第一个写请求才 500」好：后者报错里不会有「你忘了迁移」。

**冒烟与门禁的分工（别混）**：

| | `make check` | `scripts/smoke.py` |
|---|---|---|
| 回答 | 改了会不会变差 | 现在能不能用 |
| 载体 | 进程内 `TestClient` + 临时库 | 真起服务、真端口、真建库、真建 key |
| 覆盖 | 逻辑正确性、迁移可逆、指标退化 | 启动顺序、迁移时机、鉴权闭环、任务闭环、非 root |
| 服务起不来时 | **也可能全绿** | 必然红 |

`make check` 全绿而服务起不来，是这类项目最典型的交付事故：测试里 `TestClient` 自己建库、自己塞 key，「谁在什么时候建库」这整段被跳过了。

**15 项断言（local 实测全过）**：/health · /ready 与源码 `migrate.LATEST` 对账 · /ready 回报 auth=required · 无 key 401+WWW-Authenticate · 建两租户密钥 · /v1/datasets 可读 · 提交分析任务 202 · 执行完成 · 结果含主题 · 同键重放同 job_id · 同键换体 409 · 越权 404 · 台账 attempt=1 · 提交决策任务 202 · 决策出结论。

**几处刻意的写法**
- mock 下**强制 `AUTH_REQUIRED=true`**：鉴权在本地通常是关的，于是「401 → 建 key → 带 key 提交 → 越权 404」这条生产必经链路从来没被真的跑过。
- 第 02 项拿**源码的 `migrate.LATEST`** 和容器自报版本对账，而不是相信容器——镜像漏打一个迁移文件时，容器会认为自己已是最新。
- 用 3 条内联评论而非整个数据集：live 模式下 42 条就是 42 次真实调用；「数据集能读」由另一项单独验证。
- 跳过显示 `–` 而不是 `✓`。失败继续跑完（401 指向鉴权、任务不完成指向 worker，遇错即停只报第一个症状）。

**开发中测出的两个真问题（冒烟自己抓到的）**
1. `_wait_job` 忘了带鉴权头 → 轮询拿回 401，症状显示为「任务没完成」。改完后，「自欺欺人的失败」这类风险降到零：冒烟自己没鉴权就必须报错，而不是把锅甩给被测服务。
2. 断言写成 `verdict in {"GO","NO-GO",...}`，而领域层常量是 `NO_GO`。改为直接 import `domain.decision` 的常量——把结论字面量抄进冒烟，等于以后每次改枚举都要改冒烟。

**负向验证（实测）**：
```

库未迁移就起服务           → /ready 503，退出码 2（环境错误，不是「通过」）
```

**回滚章节已写进 README**，核心是顺序：
- **先回镜像，再按需回库，且优先不回库**。旧镜像 + 新库能跑（迁移都是加表加列）；新镜像 + 旧库缺表，第一个写请求就 500——那不是回滚，是制造新故障。
- 备份**不能用 `cp`**：SQLite 开着 WAL，最新提交可能还在 `-wal` 里，拷主文件会得到一个「少了一段最新数据、但看起来完全正常」的库。用 `Connection.backup()`（`make backup`）。
- `make check` 第 2 层只保证 `down()` **完整**，不保证**无损**：加表容易，删表就是把数据一起删。所以回滚只在「刚迁移完、还没产生新数据」时安全。

### P5 附带：结果归档（2026-11-18，迁移 v6）

**迁移 0006**：`jobs` 加 `archived_at` 列 + 部分索引
`(finished_at) WHERE status IN ('succeeded','failed') AND result IS NOT NULL AND archived_at IS NULL`。

**归档只清 `result`，不删行**——这是整件事唯一的硬约束。幂等靠 `UNIQUE(tenant_id, idempotency_key)`，
删行会让归档过的幂等键一起消失，同一个键重放变成新任务：**重新花一次钱，而调用方看到的响应
和正常重放一模一样**。所以行、执行台账、token 归因全部保留，只清最重的那个字段。

四个配套决定：
| 决定 | 理由 |
|---|---|
| 加 `archived_at` 而不是「result IS NULL 即归档」 | 「结果已归档」与「本来就没有结果」在 body 里长得一样，必须能分开；接口返回 `result_archived: true` |
| 部分索引 | 行一归档即退出索引，索引不随表膨胀；代价是它对别的查询没用——它本来就只为清理服务 |
| 默认 dry-run，`--yes` 才执行 | 一次能改几十万行，且误触不报错，只会让人第二天发现结果没了 |
| `--days 0` 直接拒绝 | 它的真实含义是「把刚跑完的结果立刻丢掉」，几乎不可能是本意 |

`tests/test_archive.py` 7 条，最关键的断言不是「清了多少行」而是**归档后同一幂等键重放仍返回原 job_id**。

CLI：`python scripts/jobs.py archive --days 30 [--yes]`；`make jobs-archive [YES=1]`。
实测（临时库）：预演 1 条 0.1 KiB → `--yes` 归档 1 条 → `show` 显示 `archived_at` 已写、`result` 为空 →
再次预演 0 条（已归档的不重复入选）。

⚠️ **没有定时器**：归档要外部 cron 触发。这是有意的——内置调度器会让「谁在什么时候删了结果」
变成一个应用内部的隐身行为；交给 cron，它就是一个能被看见的运维动作。

### 聚类阈值标定 v1 首轮（2026-11-18，无迁移）

**起因**：阈值 0.28 的来源是一句没有标注集支撑的注释（「hash 实测取 0.28，换 dashscope
应提到 0.55~0.65」）。而聚类当时**零评测**——`run_eval.py` 只评抽取，聚类退化不会让任何东西变红。

**先纠正一个因果错误**：`F1 0.8108` 与 embedding **无关**，它来自抽取链路。
用这个数字验收聚类是错的，本轮据此重新定义了任务（先建评测，再定阈值）。

**标注集**：`data/eval/cluster_evidence_v1.jsonl`（51 条，live+qwen-plus 实抽后冻结；v2 已扩至 216 条）+
`data/eval/cluster_pairs.jsonl`（120 对，同 59 / 异 61）。
判定标准一条：**同一条改进行动能同时解决这两条反映的问题吗**——不用「语义接近」，
否则「充电快」和「充电慢」字面最接近、经营上完全相反，会被判成同类。

**三个结论**：
1. **hash 向量没有排序结构**：同主题对 P50 0.147，不同主题对 P50 **0.160**（反了）。
   它只能当离线占位实现，不是可上线方案。
2. **极性必须进分组键**：43 对跨极性样本，判为同主题的 **0 对**。
   ARI 对照（同向量同阈值，只改分组键）：hash 0.113 → 0.535；dashscope 0.195 → **0.767**。
   两个改进乘性叠加，不能互相替代。
3. **阈值 0.65**，不是 ARI 最优的 0.56：0.56 时 `size_fit` 四条全合成一簇，含「太大」和
   「太小」，机会点不可执行；0.65 的代价是 9 个漏合（7 个集中在 `build_quality` 一条链，
   表现为同一主题分两行）。两种错的代价不对称，选可执行。

**方法学教训（值得记）**：第一版用 pairwise F1 选阈值，选了 0.56 且 F1 0.868——
但那时簇数 16 而 gold 23，**聚类等于没做**（每组恒为 1 簇，R 恒为 1.0）。
改用 ARI 才看出来。这是「指标选错会让错的方案看起来最好」的实例。

**能力边界**：最优配置下仍有 13 对误合并，全是「文本说的是同一件事、业务上不同」
（线圈烧毁×水泵失效×滤芯堵塞；渗漏×溢出；太大×太小）。向量认为它们像是对的，
它读不出部件和成因的区别。这是 embedding 的边界，不是调参问题。

→ 报极性为 `mixed`。

### 聚类重标定 v2（2026-11-21，无迁移）

**起因**：v1 的 0.65 是在 2 品类 / 120 对上标的。扩到 6 品类后两个前提塌了，
而且塌得很隐蔽——指标全部正常，只有把数据摊开看才能发现。

**三处结构变更，每一处都是被数据逼出来的**：

1. **标注单位：下标对 → 主题簇**。`SAME_PAIRS` 的 (label,a,b) 结构成本 O(n²)，
   且新增一条 evidence 会在组内新增 k 对，这些对默认判成「不同主题」——
   若其实是同主题，就是凭空造出 k 个漏检，而 F1 只是轻微下降，不会报警。
   改成「每条 evidence 归属一个簇」后人工成本 O(n)，pairs 无损派生。
   改造时验证过等价：由 v1 的 120 对反推 23 个簇再派生回 120 对，**逐对零差异**。

2. **标注粒度：粗簇 → 部件级**。v1 的 `flimsy_build` 把「连接器裂」「内部松」
   「盖扣不紧」「有毛刺」塞进一簇，这 4 项要不同的工程改动，违反了
   `make_cluster_pairs.py` 自己写的规则。实测三种粒度在 `build_quality` 上：
   粗粒度 ARI **0.460**（但 gold 只有正/负两组，**聚类按极性分就满分**，零区分力）、
   部件级 0.173、部件×失效 0.182（多数单例，不可学）。**选部件级**。

3. **分组口径：label → (dataset, label, polarity)**。生产 `analyze_reviews` 一次只处理
   一个 dataset，按 label 跨品类分组评的是不会发生的场景。导火索是 label 跨品类
   **语义漂移**：`charging_speed` 在无线充是「充电慢」、咖啡机是「出水慢」、
   电水壶是「烧水慢」、扫地机是「吸力弱」。代价：v1 的 23 对跨品类对退出评测
   （其中 9 对原判同主题），所以 **v1 的 0.65 与 v2 的 0.72 不可直接比**。

**数据规模**：evidence 51 → **216 条 / 6 品类**（新 165 条由 live 抽取产出，旧 51 条原样保留）；
主题簇 77 个；pairs 120 → **354 对**（53 组，平均 4.1 条/组，同 125 / 异 229）。

**结论**：
1. **阈值 0.65 → 0.72**。ARI 0.240 → **0.357**（P 0.580 / R 0.640），gold 簇数 117 vs 预测 120。
   bootstrap 2000 次（重采样 53 组）：P2.5 0.68 / P50 **0.72** / P97.5 0.74，
   [0.68,0.76] 覆盖 98%。**0.65 落在区间外，是实质次优**。
2. **「充电快」vs「充电慢」相似度 0.872**，是本数据全部跨极性对里最高的一对。
   这坐实了「极性必须进分组键」——向量度量语义主题，读不出行动方向。
3. **v4 不如 v3**（分离度 −0.137 vs −0.104），换大 embedding 不是解法。

**负面结论（本轮最重要，比阈值本身重要）**：单阈值向量聚类**做不到细粒度机会点归并**。
- 同主题 P10（0.623）比不同主题 P90（0.728）低 0.104，任何阈值都在重叠里取舍；
- 阈值 0.70→0.80 簇数从 107 跳到 182，中间无平滑工作点；
- 把 `build_quality` 31 条交给 qwen-plus 一次归并，它输出了**重叠分组**
  （同一条「外壳裂+塑料感廉价」落进两个主题）并漏了 1 条。
  **「一条 evidence 只属于一个主题」这个前提，粗粒度成立、细粒度不成立。**

所以「阈值收紧到小数点后两位」这个目标**不可达，原因是方法上限而非标注量**。
要输出细粒度机会点应换方法（向量粗筛 + LLM 精归并并强制单标签），继续调阈值是无效功。

**代码改动**：`config.py` dashscope 0.65 → **0.72**、hash 0.12 → 0.14；
`calibrate_cluster.py` 改为生产分组口径 + 三向量对照；
新增 `cluster_themes_v2.py`（77 簇定义 + 216 条逐条归属，单一事实源）；
新增 `extend_cluster_evidence.py`（只追加不改旧数据）；
删除 `make_cluster_pairs.py` 与 `cluster_themes.py`（被 v2 取代）。

**文件**：`cluster_evidence.jsonl`（216 条，原 51 条归档为 `_v1`）、
`cluster_pairs.jsonl`（354 对，原 120 对归档为 `_v1`）、
`vectors_{hash,v3,v4}.npy`（缓存入库，测试可离线跑）。

**守卫**：`tests/test_cluster_eval.py` 11 条，新增「0.72 优于 0.65」「v4 不如 v3」
「pairs 不含跨极性对」「pair 数等于组内组合」「正例占比不失衡」。

### 6.7 面试三句定式（对话已确认，可直接用）

- **替代评审**：没有 code review，所以把评审前置成自动化门禁（类型 + 契约测试 + 迁移可回滚），比人工更严格，因为它不疲劳。
- **替代测试岗**：没有测试同事，所以建了人工标注 gold set 和 golden 快照，指标变动有 diff——这也是发现极性判定 bug 的原因。
- **替代产品经理**：没有需求方，所以先写了「不做清单」，判据是当前规模假设下它们不解决任何真实问题。

**禁忌话术**：不要说「这个项目是我一个人做的」（等于「没人 review 过」）；要说「没有团队，所以我用机制替代了团队职能」。
