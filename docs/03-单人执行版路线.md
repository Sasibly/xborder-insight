# 单人执行版：如何一个人做出接近企业级的项目

> 本文是 `02-实施流程与验收标准.md` 的单人修订版。
> 02 回答「做什么、按什么顺序、怎么验收」；本文回答「一个人怎么做得完、以及单人条件下『企业级』到底指什么」。
> 原始估算 17.5 人天是按「有分工」假设的，单人执行必须重算——重算结果见 §4。

---

## 1. 先纠正一个误解：企业级 ≠ 架构重

多数人把「企业级」理解成技术栈复杂度：微服务、K8s、消息队列、多租户。这个理解在面试里是负资产，因为**架构复杂度只证明你会搭架子，不证明你处理过约束**。

企业里的那些东西之所以存在，原因都很具体：

| 企业里的做法 | 真实存在原因 | 单人项目该不该照搬 |
|---|---|---|
| 代码评审 | 有人会写错，且错在别人负责的模块 | 照搬会死：没有第二个人。**改为自动化门禁** |
| 独立测试岗 | 开发会高估自己代码的正确性 | **改为契约测试 + 快照回归**，成本低且可自动化 |
| DBA 管数据 | 数据丢了是事故，要有人负责 | **改为迁移脚本 + 一键重建 + 备份命令** |
| SRE 值班 | 出问题要有人 7×24 响应 | **改为结构化日志 + request_id + /metrics**，让问题能自证 |
| 产品经理定边界 | 不加边界的需求会无限膨胀 | **改为「不做清单」写进 README** |
| 项目经理排期 | 多人的活必须协调 | **改为时间盒 + 停止点**，一个人也会拖延 |

所以单人项目的「企业级」正确定义是：

> **用机制替代人。** 团队靠分工保证质量，一个人只能靠自动化、可复现和明确边界保证质量。

判断一个做法该不该做，只问一句：**它替代了哪个具体职能，还是在模仿哪个具体架构？** 前者做，后者删。

## 2. 单人 + 企业级的真实矛盾

不是工作量不够，是**缺第二双眼睛**。所有质量问题最终都归结为一件事：没人能指出你错了。

单人项目的错误分两类，处理方式完全不同：

- **能被程序发现的错**（类型错、接口不匹配、公式算错、迁移跑不通）→ 自动化门禁可以完全替代人工评审。**这一类的质量可以做到不低于团队水平，甚至更高**，因为你没有评审走过场的问题。
- **只能被人发现的错**（业务假设错了、评测标注标准漂移、方案选错了方向）→ 这个没法自动化，只能靠**外部反馈**：官方文档、真实卖家、公开评测集、把方案讲给别人听。

结论很关键：**单人项目的短板不在代码质量，在方向判断。** 所以时间分配必须反过来——代码部分压缩，验证方向的环节不能省。

## 3. 「企业级」的最低可辩护线

不是所有企业级特性都值得做。能撑住面试追问的只有下面 4 项，做完这 4 项，任何技术追问都有答案；其余是加分，不做不减分。

| 必做项 | 它替代了什么 | 缺了会怎样 |
|---|---|---|
| **① 异步任务模型** | 替代「请求-等待」的玩具模型 | 真实 LLM 下 500 条评论必超时，面试官一问就露 |
| **② 幂等提交** | 替代「重试就重建」的错误处理 | 用户刷新页面重复扣费，这是钱的问题 |
| **③ 业务参数溯源** | 替代「有人知道这个数从哪来」 | 佣金率、FBA 费写死在代码里，结论不可信 |
| **④ 版本三元组** | 替代「结果可追溯到某次运行」 | 改了 prompt，历史结论再也复现不出来 |

这 4 项的共同点：**它们都不是功能，是约束。** 功能证明你能写，约束证明你想过生产。

对照 02 文档的模块矩阵，单人版要重新裁剪：

- 02 中「必须实现 10 项」→ 单人版保留全部 10 项，但**降低实现深度**（见 §5 的降级表）
- 02 中「暂缓 5 项」→ 全部保持暂缓，**不要提前做**
- 02 中「不做 7 项」→ 追加 3 项：**CI 流水线、并发压测、多租户隔离**。理由：CI 在单人场景下等价于本地 pre-commit 脚本（成本 1/10，收益一样）；并发压测在日均 1000 任务的规模假设下没有意义；多租户隔离在没有第二个租户时无法验证，做了也只是空壳。

## 4. 时间预算重算：从「人天」改为「有效小时」

单人项目的最大错觉是「周末有两天就能做两天」。真实可用时间要考虑碎片化和状态切换成本。

**假设**：每天有效编码 2.5–3 小时（扣除环境、查文档、走神），每周 5 天，共 2 周 → **约 30 有效小时**。

按 02 的原始估算（P0 0.5 + P1 3 + P2 5 + P3 6 + P4 3 = 17.5 人天，按 6 小时/人天算约 105 小时），单人 2 周只够做 **1/3**。所以必须明确砍法，而不是硬塞。

**定稿为六个阶段**（原 02 的五阶段缺少「迭代链路」，已单列为 P4，后续阶段顺延）。预算合计 33 h，比 2 周的 30 h 溢出 3 h，用周末补或从 P2 压出。

| 阶段 | 对应链路 | 单人预算 | 占比 | 砍到什么地方为止 |
|---|---|---|---|---|
| P0 基线固化 | 实现 | 3 h | 9% | 3 个回归测试 + `make check` + **基线指标快照**（快照不可砍） |
| P1 数据地基 | 实现 | 6 h | 18% | 表结构 + 迁移 + 种子数据，不做管理界面 |
| P2 业务能力 | 实现 | 8 h | 24% | 利润模型 + 合规规则表 + 决策评分，砍掉竞争度指标 |
| P3 平台化 | **运行** | 8 h | 24% | 任务化 + 幂等 + `runs` 台账 + 成本归因，鉴权配额降级 |
| P4 迭代链路 | **迭代** | 5 h | 15% | 基线校验 + 版本对比 + bad case 回流队列，告警降为三条断言 |
| P5 交付加固 | 横跨 | 3 h | 9% | Dockerfile + 冒烟脚本 + 回滚命令，不做 CI、不做压测 |
| **合计** | | **33 h** | 100% | |

**按可用时间选档**（阶段数就是档位，不可跳阶）：

| 档位 | 阶段 | 预算 | 能讲出什么 | 讲不出什么 |
|---|---|---|---|---|
| **完整** | P0–P5（6 个） | 33 h | 「数据链路 + 三条链路全覆盖」 | — |
| **可辩护** | P0–P3（4 个） | 25 h | 业务可信 + 工程约束处理 | 改了会不会变差——无法证明 |
| **最低线** | P0–P2（3 个） | 17 h | 输入 ASIN → 输出 GO/NO-GO 与毛利 | 工程深度全靠口头补 |

25 h 档（4 阶段）是最容易踩的坑：它看起来「运维、幂等、台账都有了，很像生产系统」，但**没有迭代链路，就无法回答「改了 prompt 有没有变差」**——而这恰好是 AI 应用岗最核心的一问。所以要么做到 6 个阶段，要么老老实实停在 3 个阶段讲业务，**中间那一档是最尴尬的**。

反过来更不行：**只有工程深度没有业务模型的项目，是最容易被判为「教程项目」的**。

## 5. 降级表：同样的模块，单人怎么做

| 模块 | 团队做法 | 单人降级做法 | 损失 |
|---|---|---|---|
| 异步任务 | Celery + Redis + worker 池 | SQLite `jobs` 表 + 单进程轮询执行器 + 超时重置 | 不支持多机，但不影响正确性 |
| 幂等 | Redis 分布式锁 | 表上唯一索引 `(tenant_id, idempotency_key)` | 单机场景下完全等价 |
| 鉴权配额 | API Key + Redis 计数器 + 网关限流 | API Key 表 + 每日 token 计数落库 | 无秒级限流，但不影响成本控制 |
| 监控 | Prometheus + Grafana | `/metrics` 输出 JSON + 日志聚合到文件 | 无看板，但指标齐全 |
| 测试 | 单测 + 集成 + E2E | 契约解析单测 + golden 快照 + 冒烟 shell | 无 UI 测试（本来也没 UI） |
| 部署 | K8s + HPA | Dockerfile + compose + `.env` | 无弹性伸缩（不需要） |
| 版本可复现 | 配置中心 + 模型版本表 | `runs` 表存 `prompt_version/model/taxonomy_version` | 无 |

**降级的原则**：降「规模能力」，不降「正确性保证」。凡是「只有多机/多人时才有意义」的都可以砍；凡是「单机也会错」的都不能砍——幂等和状态落库属于后者。

## 6. 单人项目的失败模式（比技术风险更致命）

技术坑都能查，下面五个是「一个人做」特有的，而且多数项目死在这里。

| 失败模式 | 具体表现 | 机制化对策 |
|---|---|---|
| **中断后无法恢复** | 停一周回来，忘了做到哪、为什么这么设计 | 每个阶段结束写 10 行「状态卡」：做到哪、下一步、未决问题。**这条最重要** |
| **边做边改设计** | 写到一半发现表结构不对，推倒重来 | 先把数据模型写成一页纸再动手；改模型必须先改纸 |
| **完美主义拖死** | 反复优化聚类阈值，一周没进展 | 每个格子设硬时间上限，到点就锁死参数并记录「已知不足」 |
| **演示路径没跑通** | 功能都写了，但没有任何一条端到端能演示 | 每个阶段末尾必须有可运行命令；不能演示的代码不算完成 |
| **范围蔓延** | 想到什么加什么 | 新增功能必须从「不做清单」里删一项，或明确排到本轮之后 |

其中**第一条是单人项目独有的**：企业里有交接文档和同事，单人没有。状态卡成本 10 分钟，能省掉回来时半天的重建。

## 7. 两周日程（按格子执行，每格有硬上限）

| 天 | 主题 | 交付物（必须能运行） | 上限 | 超时怎么办 |
|---|---|---|---|---|
| D1 | P0 基线 | `make check` 跑通，3 个回归测试，基线指标快照 | 3h | 只留快照，测试降到 1 个 |
| D2 | P1 表结构 | 迁移脚本 + `init_db` + 种子数据，删库能重建 | 3h | 砍掉种子数据，手写 JSON 导入 |

| D4–D6 | P2 利润与评分 | `POST /v1/decision` 返回 GO/NO-GO + 毛利 + 盈亏平衡 ACOS | 9h | 砍掉竞争度指标，只留利润 + 合规 |
| D7 | **演示闭环** | 一条命令产出决策报告，能对陌生人讲 3 分钟 | 2h | 不可砍，这是唯一必须保住的一天 |
| D8–D9 | P3 任务化 | `POST /v1/jobs` → 202，`GET /v1/jobs/{id}` 查状态 | 6h | 只做内存状态机 + 落库，不做重放 |
| D10 | P3 幂等 + 台账 | 唯一索引生效，`runs` 表记录三元组与 token 成本 | 3h | 幂等保留，成本归因降为单字段 |
| D10.5 | P4 迭代链路 | `make eval` 与基线 diff，掉 2 点非零退出；`review_queue` 表 | 5h | 只做基线校验，版本对比降为一条 SQL |
| D11 | P5 容器与回滚 | `docker compose up` 能起，冒烟全绿，回滚命令可用 | 3h | 只写 Dockerfile，不做 compose |
| D12 | 收尾 | README 数字与代码输出逐项核对，状态卡归档 | 2h | 不可砍 |

### P0 落地记录（已完成 · 2026-11-17）

| 交付物 | 实际产出 | 与计划差异 |
|---|---|---|
| `make check` | `scripts/check.py` 串起测试 → 评测 → 基线 diff，三层任一不过退非零 | 无 make 环境补 `check.cmd`；Makefile 用 `.RECIPEPREFIX` 避免 TAB 被编辑器吃掉 |
| 回归测试 | **53 通过 + 1 xfail**，6 个文件 | 计划 3 个测试，实际覆盖到 HTTP 契约与极性判定——因为极性判定正是那个真 bug |
| 基线快照 | `tests/baseline.json`（F1 0.8108 / P 0.9375 / R 0.7143 / 74 token per review / P95 24ms） | 额外存了 `failing_review_ids`，用于识别「分数不变但错的地方变了」的假性稳定 |
| `make eval` | 与基线 diff，F1 掉 2 点 / P、R 单掉 5 点 / 成本超预算 / 失败集合漂移 → 非零退出 | 阈值外置到 `tests/gates.json`，改阈值等于改质量承诺，必须同步 README |

**门禁已验证能拦住真退化**：临时移除极性判定的星级兜底，`make check` 输出 F1 0.8108 → 0.6250 并退出码 1。0.6250 正是当年那个 bug 的数值，说明这类退化今后不可能被悄悄引回来。

**P0 顺手修掉的一个契约漏洞**：`{"dataset": "x", "reviews": []}` 原本返回 200（空数组为假值，被当成「没传 reviews」而静默回落到 dataset）。改成 `is not None` 判定后返回 422。这是「猜调用方意图」的典型写法，测试才暴露出来。

### P1 落地记录（已完成 · 2026-11-17）

| 交付物 | 实际产出 | 与计划差异 |
|---|---|---|
| 迁移框架 | `db/migrations/` + `migrate.py`，每迁移含 `up()/down()`，注册表校验版本号连续 | 计划说「自写迁移」，实际多做了**schema 指纹往返校验**——否则 down() 写漏没人会发现 |
| 四张表 | `reviews` / `runs` / `cost_params` / `compliance_rules` | 计划说先落 reviews + runs；实际一次落完，因为参数表的 CHECK 约束才是 P1 的真正价值 |
| 成本参数表 | 7 项，含 `value`/`source_url`/`effective_date`/`verified_at`，**全为 draft、value 全 NULL** | 没有预置任何数值，见下方「为什么不填数」 |
| 合规规则表 | 4 条，无线充电器 × 美国，`blocker`/`warning` 分级，全为 draft | 同上 |
| 门禁第二层 | `--db-only`，临时库跑 `up→down→up` 比对指纹 | 计划外的收益：顺手抓到一个真问题 |

**为什么不填数**：佣金率、FBA 费、税率都随类目与政策变化，必须来自官方文档。凭印象填一个「大概 15%」会制造 ②类错误——系统正常返回、结论是错的，页面上完全看不出来。所以种子数据只声明「需要核实什么」，`value` 留空。

代价是诚实的：**P2 的利润模型现在算不出结论**（会抛 `param_unverified`，HTTP 503）。这是有意接受的——算不出来会报错，算错了没人知道。

**门禁抓到的一个真问题**：故意让 `down()` 漏删 `cost_params`，门禁报「down(0) 后残留表：['cost_params']」并退出码 1。更有价值的是修复过程本身：`roundtrip()` 最初在看残留之前就重建，结果撞上 "table already exists"，把「down 删漏」伪装成一个语法错误。**错误信息指向的地方不是问题所在**，这才是最贵的 bug。现在改成发现残留立即返回诊断。

**三条可复用的判断**：

1. **约束写进数据库，不写进文档**。「verified 必须有来源」如果只写在 README 里，第一个赶时间的人就会绕过它。写进 CHECK 后，连直接 `UPDATE` 都绕不过去。
2. **`get(key, default)` 是有害的 API**。default 把「参数缺失」变成静默降级，利润模型用 0.15 的默认佣金率算出的毛利看起来完全正常。`require()` 主动抛错才是对的。
3. **迁移的 down() 必须被自动验证**。人工 review 看不出漏删，只有跑往返才知道。

- **P2 可以直接继承**：`params.require()` 是利润模型的唯一取数入口；`runs` 的 `params_snapshot` 让「当时用的哪版费率」可回溯。

### P3 落地记录（核心已完成 · 2026-11-17）

| 交付物 | 实际产出 | 与计划差异 |
|---|---|---|
| 任务模型 | `jobs` 表 + 状态机 `queued → running → succeeded/failed`（`failed → queued` 仅限重试） | 计划说「状态存内存」是可接受降级，**实际直接落库并加租约**——因为降级表里那句「只做内存状态机」会让 D12 的「重启后不卡死」根本无法演示 |
| 执行器 | `jobs/runner.py`，`serve()` 常驻 + `drain()` 同步语义 | 加了 `drain()`：异步常驻的测试只能「等一会儿再断言」，那种测试迟早 flaky |
| 幂等 | `UNIQUE(tenant_id, idempotency_key) WHERE key IS NOT NULL` + 请求体指纹比对 | 计划只说「唯一索引生效」，实际补了**指纹冲突检测（409）**——只做唯一索引会把「同键换内容」变成静默复用旧任务 |
| 防卡死 | 租约 `lease_expires_at` + 心跳续租（租约 1/3 周期） | 计划是「重启时把 running 改回 queued」，那在多实例下会误杀别人正在跑的任务；改租约后单/多实例都成立 |
| 台账接线 | `runs.job_id` + `attempt`，`UNIQUE(job_id, attempt)` 部分索引 | 计划只要求「记录三元组与 token」，实际把 `runs` 与 `jobs` 的职责分开并加了唯一索引，保证同一次尝试只记一笔账 |

**三条可复用的判断**：

1. **幂等必须靠唯一索引，不能靠「先查再插」**。后者在并发下必然漏：两个请求同时查到「不存在」，然后都插入。正确顺序是直接 INSERT，撞键后回查。
2. **同一个幂等键 + 不同请求体必须报错**。返回旧任务是"最省事"的实现，但它让调用方以为新参数已被接受，实际跑的是老参数——结论错了却全程无报错。
3. **状态机要区分「执行」与「请求」**。`runs` 的终态不可回退（一次执行结束了就是结束了）；`jobs` 的 `failed` 可回 `queued`（一次请求可以再算一次），但必须复用同一个 `job_id`，否则幂等失效。

**顺手修掉的两处**：① `JobRunner(handlers={})` 因 `handlers or HANDLERS` 被静默替换成默认注册表，空注册表等于「什么都不处理」而不是「没传」；② 分析任务的数据源加载失败时不写 `runs` 台账，导致「失败的尝试在账上不存在」——改成台账先开、再取数。

**负向验证**：短路幂等指纹比对后，库层 + HTTP 层各红一条测试；恢复即绿。

### P3b 落地记录（鉴权与配额 · 2026-11-18）

| 交付物 | 实际产出 | 与计划差异 |
|---|---|---|
| 密钥 | `api_keys`（sha256 主键、`revoked_at`、日额度、RPM）+ `scripts/keys.py` | 计划只要求「哈希存储 + 可吊销」，实际补了 `stale` 轮换提醒与「前缀吊销必须唯一匹配」——按前缀猜着吊销会误杀生产密钥 |
| 租户派生 | `Principal` 只从密钥来；请求体带 `tenant_id` → 422 | 计划写的是「由密钥派生」，没写清违背时如何失败；靠 `extra="forbid"` 让它在契约层就炸，而不是被静默忽略 |
| 隔离 | `get_scoped` 把越权当不存在（404） | 计划没说越权返回什么。403 会确认 id 存在，等于送给对方一个 job_id 探测接口 |
| 限流 | `rate_limits` 落库 + `UPSERT ... RETURNING` | 计划写「令牌桶」。改成固定窗口：令牌桶要额外存「上次补充时间」，收益在这个量级看不到；边界突发 2 倍已写进已知限制 |
| 配额 | 聚合 `jobs` 台账，不另建计数器 | 计划要求「日 token 配额」，没指定来源。用计数器必然漂移，用台账则天生对账 |

**三条可复用的判断**：

1. **被拒的请求也必须计数**。计数若与抛错在同一个事务里回滚，「一直被拒」就成了绕过限流的方法——重试多少次都停在第一个请求。
2. **越权要返回「不存在」，不是「禁止」**。403 是「这个 id 存在但不给你看」，在资源 id 可枚举的接口上等于信息泄漏。
3. **安全开关的默认值必须跟着运行模式走**。`AUTH_REQUIRED` 在 live 下默认开启，关闭时启动日志与 `/ready` 双处留痕——「忘了开鉴权」不会有任何报错，这是它最危险的地方。

**顺手修掉的两处**：① 前缀吊销原先只查未吊销的 key，导致运维脚本重跑时报「找不到」，现改为幂等且只在前缀歧义时拒绝；② 同步分析接口关闭时，替代路径只写在 `detail` 里（对外不可见），等于告诉调用方「不行」却不说怎么办，已并入 `message`。

**负向验证**：短路归属校验 → 2 条测试红；让被拒请求不计数 → 1 条红，断言消息直接写出「限流可以被一直重试绕过」。两条都恢复即绿。

**一处刻意未做**：同步 `/v1/analyze` 不落台账、因此绕过配额。没有去补记账，而是让它在 live 下默认关闭（`SYNC_ANALYZE_ENABLED`）——补齐记账要动 `runs` 的租户维度，成本大于收益，而它本来就不该是生产入口。

### P5 落地记录（交付加固 · 2026-11-18）

| 交付物 | 实际产出 | 与计划差异 |
|---|---|---|
| 镜像 | 两阶段 `Dockerfile`、非 root（uid 10001）、`HEALTHCHECK` 打 `/ready`、`requirements.lock` | 计划只写「多阶段 + 非 root + 探针」。补了 `.gitattributes` 钉死 `*.sh` 为 LF——Windows 上 CRLF 会让入口脚本报 `exec format error`，报错完全不提换行符 |
| 启动顺序 | `docker-entrypoint.sh`：先 `db.py up`，再 `exec uvicorn` | 计划里没有这一项。**迁移必须在入口做**，放进应用等于「任何一个进程都可能改库结构」，多实例时就是两个进程同时跑 DDL |
| 冒烟 | `scripts/smoke.py`，15 项断言，三目标 local/docker/remote，`smoke.cmd` 对称入口 | 计划是「起容器 → 断言」，实际做成目标可切换：本地没有 Docker daemon 时仍能验证代码链路，这个能力在开发机上比容器路径更常用 |
| 回滚 | README「交付：镜像、冒烟、回滚」章节 + `make backup` / `make rollback` | 计划只写「把命令写进 README」。写的时候才想清楚**顺序**：先回镜像再回库，且优先不回库——旧镜像 + 新库能跑，新镜像 + 旧库缺表必 500 |
| 归档 | 迁移 v6：`archived_at` + 部分索引；`jobs.py archive` | 原计划列为「可选」。真做时发现关键约束：**不能删行**，否则幂等键一起消失，重放变新任务、重新花钱 |

**三条可复用的判断**：

1. **门禁和冒烟回答的是两个问题**。`make check` 全绿而服务起不来，是这类项目最典型的交付事故——测试里 `TestClient` 自己建库、自己塞 key，「谁在什么时候建库」整段被跳过。所以冒烟必须真起进程、真走端口。
2. **探针要打 `/ready` 而不是 `/health`**。`/health` 只证明进程活着；用它的容器会「健康地」接流量然后全量 500。同理，探针的 `start-period` 必须够迁移跑完，否则首启被判死 → 重启 → 再判死。
3. **归档清的必须是字段，不是行**。行里扛着幂等键。凡是想「清理」这张表的方案，先问一句「删掉的那行里有没有别人依赖的约束」。

**负向验证**：`AUTH_REQUIRED=false` 起服务 → 冒烟第 03、04 项变红、退出码 1；库未迁移就起服务 → `/ready` 503、退出码 2（环境错误，不冒充通过）。

## 8. 怎么把「一个人做的」讲成优势

这是本文最实用的一节。单人项目在面试里的默认扣分项是「没人验证过」，而恰恰这一点可以反转。

**不要说**：「这个项目是我一个人做的」——这句话在面试官耳朵里等于「没人 review 过」。

**要说**：「这个项目没有团队，所以我用机制替代了团队职能」——然后给出三句具体的话：

1. **替代评审**：「没有 code review，所以我把评审前置成自动化门禁：类型检查 + 契约测试 + 迁移可回滚，任何一项不过提交不进去。这比人工评审更严格，因为它不疲劳。」
2. **替代测试岗**：「没有测试同事，所以我建了人工标注的 gold set 和基线快照。F1 每次变动都有 diff，指标下降会立刻暴露。这也是我发现极性判定 bug 的原因——而且现在这句话可验证：把那处兜底删掉，`make check` 当场报 F1 0.81 → 0.63、退出码 1。」
3. **替代产品经理**：「没有需求方，所以我先写了『不做清单』：平台爬虫、支付计费、多租户前端、K8s 全部排除。判据是当前规模假设下它们不解决任何真实问题。」

这三句话的价值远高于「支持多租户、高并发、日活百万」。因为**它们展示的是判断力，而判断力无法伪造**。

配套的追问准备（每个都要能答三层）：

| 追问 | 第一层 | 第二层 | 第三层 |
|---|---|---|---|
| 为什么不用 Celery？ | 单机日均千级任务，表 + 轮询够用 | 需要多 worker 抢任务或跨机时才必须上 | 现方案的短板是重启丢进行中任务，用超时重置兜住 |
| 幂等怎么做的？ | 唯一索引，不是分布式锁 | 单机场景下唯一索引严格等价且零额外依赖 | 冲突时返回原结果而非报错，语义要定义清楚 |
| 参数错了怎么办？ | 参数表带来源和日期，可审计 | 来源限定官方文档，不采信二手攻略 | 数值变更走迁移，历史 run 保留当时快照 |
| F1 只有 0.81 怎么解释 | 剩下的是间接表达和中文口语 | 这是规则基线的上限，不是方案上限 | 接真实 LLM 后重测，预期到 0.9 附近，成本 X |

## 9. 一句话结论

一个人做，正确的目标不是「让项目看起来像一个团队做的」，而是**「让项目在没有团队的情况下依然具备可验证性」**。

可验证性来自三样东西：能一条命令复现的数字、有出处的参数、能讲清取舍边界的决策记录。这三样都不依赖人数，所以单人也能做到，而且做得比堆架构更有说服力。
